# 운영 핫픽스

운영에서 결제 검증을 우회하는 사례가 발견됐다. `PaymentValidator.validate`를 지금 보강해야 한다. 빨리 고쳐야 하지만 운영 코드이므로 평가는 오히려 더 보수적이어야 한다. 이 튜토리얼은 운영 키워드가 어떻게 판정을 바꾸는지, HOLD와 STOP이 나오면 무엇을 해야 하는지, 왜 이 상황에서 `vibe`를 쓰면 안 되는지를 다룬다.

- **소요 시간** — 분석과 적용 30분 내외. 회귀 테스트 채우기와 재평가는 변경 크기에 따라 다르다.
- **전제** — 하네스와 인덱스가 있다. 장애 대응 중이라도 프로젝트 루트에서 Claude Code를 연다.
- **이 튜토리얼이 다루는 스킬·에이전트** — `trace-logic`, `analyze-impact`, `test-generator`, `safe-modify`(mode=hotfix), `change-safety`, `doc-syncer`.

## 준비

운영 모드는 사용자 문장에서 자동 감지된다. `safe-modify` Phase 0의 키워드 표를 미리 알아 두면 의도한 모드가 적용된다.

| 문장에 포함된 키워드 | mode | change-safety 조정 |
|---|---|---|
| "운영 패치", "프로덕션", "운영 배포" | `production` | 보안 가중치 ×2, 즉시 STOP 임계값 하향 |
| "긴급 핫픽스", "장애 대응" | `hotfix` | 변경 라인 수 임계 ×0.5 — 작은 변경만 GO |
| "레거시 손보기", "옛날 코드" | `legacy` | 컨벤션 가중치 ×0.5 |
| "고객 데모", "데모 직전" | `customer_facing` | 외부 시스템 영향 가중치 ×2 |
| 없음 | `normal` | 기본 |

핫픽스 요청에는 "긴급 핫픽스"를 문장에 넣는다. 운영 배포까지 같은 세션에서 다루면 "운영 패치"도 함께 쓴다.

## 단계별 진행

### 1. 원인 위치 좁히기 (선택)

오류 위치가 아직 불명확하면 흐름부터 본다.

```text
결제 검증 오류 나고 있어. 관련 로직 추적해줘
```

`trace-logic`이 진입점부터 DB까지 경로를 `_workspace/reports/trace_<slug>.md`에 남긴다. 에러 로그가 있으면 붙여 넣어 호출 스택을 역추적하게 한다.

### 2. 영향도 먼저

```text
긴급 핫픽스 — PaymentValidator.validate 보강해야 해. 영향도 먼저
```

`analyze-impact`가 `_workspace/reports/impact_PaymentValidator_validate.md`를 만든다. 시나리오 예시에서는 MEDIUM(5/10)이고 외부 결제 게이트웨이 호출이 경로에 포함돼 있다. 리포트의 "외부 통신 영향" 절에 대상 시스템이 적혀 있고, 사전 체크리스트에 "(외부 통신 영향) API 계약 변경 합의"가 들어 있다. 장애 상황에서도 이 단계를 건너뛰지 않는다. 영향 범위를 모르고 고치면 두 번째 장애를 만든다.

### 3. 회귀 테스트 먼저 만들기

```text
회귀 테스트 먼저 만들어줘
```

`test-generator`가 `pattern_profile.py`로 test 레이어 프로필을 고르고 기존 테스트 컨벤션(명명·assertion 라이브러리·픽스처·mocking) 그대로 골격을 만든다. 영향도가 높을수록 케이스가 많아진다(LOW 1~2개, HIGH 5~10개). 결과 요약은 `_workspace/reports/tests_<slug>.md`에 있다.

생성된 테스트에는 다음 주석이 들어 있다.

```java
// TODO: assertion 보완 — 비즈니스 규칙에 맞는 정확한 결과 검증 필요
```

비즈니스 검증은 사람이 채운다. 결제 검증 우회 사례를 재현하는 케이스를 반드시 추가한다. 이 단계는 `safe-modify` Phase 1이 CRITICAL일 때의 선택지 2("사전 회귀 테스트 작성 후 진행")로도 들어갈 수 있다.

### 4. 핫픽스 모드로 안전 변경

```text
이 변경 안전하게 적용해줘 — 긴급 핫픽스. validate()에서 금액이 0 이하이거나 통화 코드가 허용 목록에 없으면 예외
```

`safe-modify`가 `mode=hotfix`로 진행한다. 어댑터 커버리지·패턴 선택·영향 확인을 거쳐 변경을 적용하고, `pattern-conformance` → `verify-target.mjs run` → `change-safety` 순으로 평가한다. hotfix 모드에서는 변경 라인 수 임계가 절반이므로 작은 변경만 GO가 된다. 크게 고치고 싶다면 핫픽스와 근본 수정을 분리하라는 신호다.

### 5. HOLD가 나왔을 때

시나리오 예시에서는 보안 점수 6/10으로 HOLD가 나온다.

```text
결정: HOLD

보완 필요 항목:
1. 보안 영향: 외부 입력 검증 누락 — 입력 검증 강화 패턴 추가
보완 후 다시 호출하세요: "이 변경 다시 평가해줘"
```

HOLD는 "주의 후 진행"이다. `_workspace/reports/safety_<slug>.md`의 차원별 표에서 점수가 높은 차원과 근거를 찾고, 권고된 보완을 적용한다. 그 뒤 재평가한다.

```text
이 변경 다시 평가해줘
```

보완이 반영되면 GO로 바뀐다. 하네스는 HOLD 상태에서 자동으로 코드를 고치지 않는다. 판단은 항상 사람이 한다.

### 6. STOP이 나왔을 때

STOP은 "현재 방식 중단"이다. 다음 중 하나가 발견됐다는 뜻이다.

- 즉시 STOP 트리거 — 평문 비밀번호·API 키 추가, SQL 인젝션 가능 패턴, 인증·인가 우회 코드, TRUNCATE·DROP·WHERE 없는 DELETE, 운영 환경 전용 분기에 검증 없음.
- 보안 점수 8 이상 또는 종합 위험도 6 초과.
- 패턴 FAIL 또는 필수 검증 명령 실패.

리포트의 "대안" 절에 다른 접근·단계적 분할·사전 작업이 제시된다. 그 대안을 놓고 논의한다. 판정을 우회하거나 무시하는 방법은 의도적으로 제공되지 않는다. 결제 검증처럼 인증·인가에 가까운 코드는 STOP 트리거에 걸리기 쉬우므로 대안이 "검증 로직을 별도 클래스로 분리하고 기존 경로는 유지"처럼 나오면 그 방향으로 새 변경을 시작한다.

### 7. 배포와 문서

GO가 나오면 Phase 5가 인덱스와 wiki를 자동 갱신한다. 커밋과 canary 배포는 사람이 한다. 시나리오 흐름은 canary 배포 → 안정성 확인 → 전체 배포다. `production` 모드였다면 보고에 "단계적 배포" 권고가 함께 나온다.

배포 뒤 문서를 맞춘다.

```text
변경 사항 문서 동기화
```

`doc-syncer`가 `_workspace/reports/docs_sync_<slug>.md`에 CHANGELOG·ADR·CLAUDE.md 변경 이력 항목 권고를 만든다. 자동 수정은 하지 않으며 "전체 적용 / 선택 적용 / 권고만 확인" 중 고르면 된다.

## vibe를 쓰면 안 되는 이유

"그냥 빨리 고쳐"라고 말하고 싶은 순간이지만, 이 상황에서 `vibe`는 맞지 않는다.

- `vibe`는 `analyze-impact`·`pattern-conformance`·`change-safety` 게이트를 생략한다. 운영 모드 가중치도, 즉시 STOP 트리거 검사도 적용되지 않는다. 결제 검증 우회 같은 보안 문제는 바로 이 검사가 잡아내는 항목이다.
- 핫픽스는 `vibe`의 승격 조건에 자주 걸린다. 외부 API 계약 변경, 트랜잭션 경계 변경, 3개 이상 파일 수정, DB 스키마 변경 중 하나라도 해당하면 `vibe`는 그 자리에서 멈추고 `safe-modify`로 승격한다. 이미 고친 파일은 되돌리지 않고 승격된 스킬의 영향 분석에 포함시킨다. 결국 같은 게이트를 통과해야 하므로 처음부터 `safe-modify`로 가는 편이 빠르다.
- `vibe`는 사용자가 "알아서/그냥/바이브"라고 명시했을 때만 뜬다. "고쳐줘"·"수정해줘"의 기본 경로는 `safe-modify`다.

`vibe`가 맞는 자리는 UI 문구 수정처럼 영향 범위가 한눈에 보이는 국소 변경이다. 운영 장애 대응은 그 반대편이다.

## 결과 확인

- `_workspace/reports/impact_PaymentValidator_validate.md` — 외부 통신 영향과 사전 체크리스트.
- `_workspace/reports/tests_<slug>.md`와 생성된 테스트 파일 — 우회 사례 재현 케이스가 채워져 있어야 한다.
- `_workspace/reports/safety_<slug>.md` — 1차 HOLD 근거와 재평가 GO 결과. 파일은 재평가 시 덮어쓰이므로 1차 결과를 남기려면 복사해 둔다.
- `_workspace/reports/docs_sync_<slug>.md` — CHANGELOG·ADR 권고.

## 막혔을 때

- **모드가 `normal`로 잡혔다** — 문장에 키워드가 없었다. "긴급 핫픽스"나 "운영 패치"를 넣어 다시 요청한다. 모드는 `change-safety`에 전달되어 가중치만 바꾸며 절차는 같다.
- **재평가에서도 HOLD다** — `safety_<slug>.md`의 차원별 근거를 보면 어느 차원이 남아 있는지 나온다. 테스트 적정성이면 assertion을 채우고 테스트를 실제로 실행해야 한다. 미실행은 PASS가 아니다.
- **테스트가 없는 레거시 모듈이다** — `test-generator`는 기존 테스트가 전혀 없으면 프레임워크·명명·fixture 방식을 확인하기 전 생성하지 않는다. 확인 질문에 답하면 진행된다.
- **인덱스가 stale이라 시간이 걸린다** — 장애 중 재인덱싱이 부담되면 건너뛸 수 있지만 이후 판정에 `지식 모델 stale`이 명시된다. 그 구간은 소스를 직접 대조한다.
- **외부 결제 게이트웨이 호출이 경로에 있다** — impact 리포트가 "운영 테스트 필요"를 표시한다. mock 테스트로는 부족하니 canary 단계에서 실제 연동을 확인한다.
- **핫픽스 중 마이그레이션 진행 중인 모듈을 건드린다** — 일반 수정과 마이그레이션은 동시에 가능하지만 대상 모듈 충돌만 주의한다. 매핑 테이블에 해당 모듈이 있으면 마이그레이션 담당자와 조율한다.
