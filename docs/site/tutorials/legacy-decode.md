# 레거시 코드 해석

변수명이 `a1`·`b2`인 PL/SQL 프로시저 `PROC_BATCH_NIGHT`를 받았다. 주석도 문서도 없고 원작자는 떠났다. 이 튜토리얼은 `legacy-decoder`를 직접 호출해 `decoded_<slug>.md`를 받고, 1~10절과 오늘 추가된 11절 청중별 요약을 읽는 법, `[추정]` 마크와 의문점을 다루는 법, 결과를 인수인계 문서로 쓰는 법을 다룬다.

- **소요 시간** — 해석 수 분, 리포트 읽기 20분, 업무 담당자 확인은 별도.
- **전제** — 하네스가 있으면 호출 컨텍스트(7절)가 채워진다. 없어도 코드만으로 1~6절은 나온다.
- **이 튜토리얼이 다루는 에이전트·스킬** — `legacy-decoder`(직접 호출), 이후 `analyze-impact`, `review-sql`.

## 준비

대상을 특정한다. 파일 경로·프로시저명·클래스명 중 하나면 되고, 코드를 붙여 넣어도 된다. `.claude/agents/domain-expert.md`가 있으면 비즈니스 의도 추정에 도메인 지식이 활용된다.

`legacy-decoder`는 분석·문서화만 한다. 코드를 수정하거나 리팩터링을 권고하지 않는다. 수정 여부는 리포트를 읽은 뒤 사용자가 결정한다.

## 단계별 진행

### 1. 직접 호출

```text
PROC_BATCH_NIGHT 뭐하는 거야?
```

"이 PL/SQL 해석해줘", "이 COBOL 모듈 설명", "이 클래스 뭐하는 거야? [코드 붙여넣기]"도 같은 에이전트를 부른다. 에이전트는 다음 순서로 분석한다.

1. 구조 분해 — 진입점·분기점·루프·외부 호출·출구.
2. 변수 의미 추적 — 할당 우변과 사용 문맥으로 의미를 추정하고 `[추정]`을 붙인다.
3. 비즈니스 의도 추정 — 테이블명·외부 시스템명·분기 로직에서 역추출.
4. 사이드 이펙트 — DB 변경, 파일 IO, 외부 호출, 전역·세션 변경.
5. 데이터 흐름 — 입력 → 변환 → 출력.
6. 호출 컨텍스트 — `call_graph.json`으로 호출자, 호출 시점, 트랜잭션·보안 컨텍스트.

결과는 `_workspace/reports/decoded_<slug>.md`에 기록된다(예: `decoded_PROC_BATCH_NIGHT.md`).

### 2. 1~10절 읽기

리포트 머리에는 대상·라인 수·복잡도 추정(LOW/MEDIUM/HIGH/EXTREME)이 있다. 절별로 무엇을 보는지 정리하면 다음과 같다.

| 절 | 내용 | 읽는 요령 |
|---|---|---|
| 1. 한 문장 요약 | 코드가 무엇을 하는지 | 업무 담당자에게 확인할 첫 문장 |
| 2. 비즈니스 의도 | 3~5줄, `[추정]` 다수, 근거 목록 | 근거가 테이블명·변수명 중 무엇인지 본다 |
| 3. 단계별 동작 | Step마다 코드 위치·입력·처리·출력 | 수정할 때 진입점으로 쓴다 |
| 4. 변수 사전 | 변수명·추정 의미·라인·출처 표 | `a1 → [추정] 사용자 ID (DB 조회 결과 첫 컬럼)` 형태 |
| 5. 사이드 이펙트 | 어떤 테이블을 INSERT/UPDATE/DELETE, 외부 호출, 파일 IO | 운영 영향이 여기서 결정된다 |
| 6. 데이터 흐름 | 입력 → 변환 → 출력, 3단계 이상이면 Mermaid flowchart | 분기는 마름모, 노드 15개 이하, 코드에 없는 단계는 그리지 않는다 |
| 7. 호출 컨텍스트 | 호출자, 동기/비동기/스케줄, 트랜잭션 경계, 보안 컨텍스트 | 인덱스가 없으면 비어 있을 수 있다 |
| 8. 위험 신호 | 동적 SQL 결합, 트랜잭션 안 외부 호출, 데드락 패턴, 매직 넘버 | 수정 시 건드리면 위험한 곳 |
| 9. 의문점 | 코드만으로 결정 불가한 항목 | 사람에게 물을 목록 |
| 10. 신뢰도 | 동작 해석·비즈니스 의도 각각 HIGH/MEDIUM/LOW와 사유 | LOW면 2절을 결론으로 쓰지 않는다 |

6절의 flowchart는 그대로 복사해 문서에 붙일 수 있다.

### 3. 11절 청중별 요약 읽기

11절은 1~10절을 읽는 사람에 따라 다시 쓴 것이다. 새 사실을 더하지 않고 `[추정]` 마크도 그대로 유지하며 각 3~6줄이다.

- **아키텍트** — 이 코드가 시스템 어디에 놓이는지. 호출자·의존 모듈·트랜잭션 경계·외부 통신과, 교체·분리 시 끊어야 할 결합 지점. 마이그레이션 계획의 인벤토리와 함께 읽는다.
- **개발자** — 수정할 때 먼저 볼 진입점과 라인, 8절의 위험한 곳, 검증에 쓸 입력·출력 지점, 관련 SQL ID·테이블. `safe-modify`를 시작하기 전 체크리스트로 쓴다.
- **업무담당자** — 업무 용어로만 쓴다. 어떤 업무를 처리하는지, 적용되는 규칙과 예외, 어떤 데이터가 바뀌는지. 클래스·메서드·변수 이름이 나오지 않고, 9절의 의문점이 질문 형태로 바뀌어 있다. 이 절을 그대로 업무 담당자에게 보내면 된다.

11절에서 새로운 해석이 시작되거나 추정이 확정으로 바뀌어 있으면 에이전트 원칙 위반이다. 1~10절과 대조해 이상하면 다시 호출한다.

### 4. `[추정]` 마크와 의문점 다루기

신뢰 기준은 단순하다. 코드에서 직접 읽힌 것(변수 흐름, 사이드 이펙트, 호출 관계)은 신뢰할 수 있고, `[추정]`이 붙은 비즈니스 의도는 사람 확인이 필요하다.

절차는 다음과 같다.

1. 9절 의문점과 11절 업무담당자 절의 질문을 업무 담당자에게 보낸다. "왜 이 분기가 있나, 비즈니스 규칙인가 임시 대응인가"처럼 코드로는 답이 안 나오는 것들이다.
2. 답을 받으면 리포트 해당 절 아래에 확인 일자와 답변자를 적어 남긴다. `_workspace/reports/` 파일은 하네스가 다시 쓰지 않으므로 직접 편집해도 안전하다.
3. 확인된 항목의 `[추정]`은 지우지 않고 "확인됨 — 답변자·일자"를 덧붙인다. 원래 추정이었다는 사실이 다음 사람에게 유용하다.
4. 답을 못 받은 항목은 그대로 둔다. 자동 추측보다 모른다고 남기는 것이 낫다.

### 5. 영향도로 이어 가기

해석이 끝나면 수정할지 결정한다. 그 전에 호출 위치와 영향 SQL을 본다.

```text
이 프로시저 영향도 분석해줘
```

`analyze-impact`가 `_workspace/reports/impact_PROC_BATCH_NIGHT.md`를 만든다. 8절 위험 신호에 동적 SQL 결합이 있었다면 `review-sql`로 인젝션 위험을 별도 점검한다. 반대로 `review-sql`이 "주석 없는 대형 프로시저"를 만나면 `legacy-decoder`를 권고하므로 두 스킬은 서로를 부른다.

리팩토링을 결정했으면 `safe-modify`로 진행하고, 11절 개발자 절을 변경 범위 확인에 쓴다.

### 6. 인수인계 문서로 쓰기

`decoded_*.md`는 `_workspace/reports/` 아래에 있다. 이 폴더는 재생성 가능한 산출물로 취급되어 `.gitignore` 대상이 되기 쉽고, `publish-wiki`도 `_workspace/wiki/`와 `_workspace/**/*.json`만 발행하므로 리포트 `.md`는 자동으로 넘어가지 않는다. 인수인계에 쓰려면 다음 중 하나를 택한다.

- 확인 답변까지 반영된 리포트를 프로젝트 문서 폴더(예: `docs/legacy/`)로 복사해 커밋한다.
- 11절의 세 절을 청중별로 잘라 배포한다. 아키텍트 절은 설계 리뷰 자료로, 개발자 절은 담당자 온보딩 체크리스트로, 업무담당자 절은 업무 확인 회의 자료로 쓴다.
- 6절 Mermaid flowchart를 wiki나 Confluence 페이지에 붙여 시각 자료로 남긴다.

절차 전체는 [담당자 교체·인수인계](/tutorials/handover.md)에서 다른 산출물과 함께 묶는다.

## 결과 확인

- `_workspace/reports/decoded_<slug>.md` — 11절까지 채워진 리포트. 6절에 flowchart가 있으면 코드 단계가 3개 이상이었다는 뜻이다.
- 10절 신뢰도 — 동작 해석 HIGH, 비즈니스 의도 MEDIUM 이상이면 바로 쓸 수 있다.
- 9절 의문점에 대한 업무 담당자 답변 기록.
- (선택) `_workspace/reports/impact_<slug>.md` — 수정 결정을 위한 호출 위치.

## 막혔을 때

- **7절 호출 컨텍스트가 비어 있다** — 인덱스가 없거나 프로시저가 외부 스케줄러에서만 호출된다. "인덱스 갱신해줘"로 갱신하고, 스케줄러·트리거 호출은 정적 분석에 잡히지 않으므로 운영팀에 확인한다.
- **신뢰도가 LOW다** — 사유가 10절에 있다. 변수명이 전부 불분명하거나 도메인 지식이 없을 때 그렇다. 업무 담당자 답을 받아 2절을 보강한 뒤 다시 호출하면 근거가 늘어난다.
- **결과가 너무 길다** — God class 수준(5000줄+)이면 진입점별로 나눠 호출한다. "PROC_BATCH_NIGHT의 정산 부분만 해석해줘"처럼 범위를 좁힌다.
- **리팩토링 제안을 기대했다** — 이 에이전트는 해독만 한다. 수정은 `safe-modify`, 재작성은 `scaffold-feature`, 스택 전환은 `plan-migration`이 담당한다.
- **결과를 신뢰할 수 있나** — 직접 읽힌 것은 신뢰 가능하고 추정은 `[추정]` 마크로 구분된다. 마크가 없는데 추정처럼 보이는 문장이 있으면 그 부분을 지적하고 다시 호출한다.
- **다른 언어인데 되나** — COBOL, PL/SQL, Forms 4GL, Old VB, Classic ASP, Old Perl, Struts 1, EJB 2, JSP scriptlet, classic ADO.NET, 동적 SQL·저장 프로시저·트리거 체인이 지원 목록에 있다.
