# 모범 사례

하네스를 한 번 만든 뒤 매일 쓰면서 지키면 좋은 습관을 모았습니다. 인덱스를 최신으로 유지하는 법, 세션을 나누어 토큰을 아끼는 법, 상황에 맞는 스킬을 고르는 법, HOLD/STOP 판정을 받았을 때의 태도, 그리고 팀 저장소에 무엇을 커밋할지에 관한 정책입니다. 초기화를 마친 직후와 팀에 하네스를 도입할 때 읽어 두면 좋습니다.

## 인덱스 신선도를 유지한다

인덱스 기반 스킬(`analyze-impact`·`safe-modify`·`trace-logic`·`find-feature`)은 실행 전에 `build-index.mjs --check-stale`로 소스 지문과 인덱스를 비교합니다. exit 0이면 그대로 진행하고, exit 1이면 인덱스가 없을 때는 `--mode init`, 소스가 바뀌었을 때는 `--mode incremental`로 재인덱싱한 뒤 진행합니다. 재인덱싱이 불가능하면 리포트에 `지식 모델 stale` 경고를 명시합니다. 따라서 일상 작업에서 인덱스가 조용히 낡아 있을 일은 드물지만, 다음 습관이 결과를 더 안정적으로 만듭니다.

| 상황 | 권장 문구 | 실행 범위 |
|------|-----------|-----------|
| 리팩터링·의존성 변경·DB 스키마 변경 직후 | "인덱스만 갱신해줘" | 인덱스 증분 갱신만 (LLM 전체 분석 없음) |
| 팀 컨벤션이 바뀜 | "패턴만 다시 추출해줘" | pattern-extractor + 프로필 검증 |
| 새 기능 대거 추가 | "하네스 업데이트해줘" | 백업 후 incremental 분석 + 재실행 |
| 마이그레이션 완료 등 구조 대변경 | "하네스 다시 초기화해줘" | 백업 후 전체 재실행 |

터미널에서 직접 확인하려면 다음 명령을 씁니다. `$env:CLAUDE_PLUGIN_ROOT`는 플러그인 설치 루트입니다.

```powershell
node "$env:CLAUDE_PLUGIN_ROOT/agents/lib/build-index.mjs" --root "D:\work\order-service" --check-stale
```

`--mode incremental`은 소스에서 그래프를 다시 만들기 때문에 손으로 인덱스 JSON을 고쳐 두면 다음 갱신에서 사라집니다. analyzer의 판정이 `_ai_patch.json`으로 분리돼 있는 이유이며, 인덱스 파일을 직접 편집하지 마세요.

## 세션을 분리한다

초기화가 끝난 시점은 대화 컨텍스트가 가장 큰 순간입니다. Phase 3.6 메뉴에서 "지금 안 함"을 고르고, wiki와 경계 QA는 새 세션에서 따로 실행하세요. 같은 결과를 더 적은 토큰으로 얻습니다.

```text
(새 세션)
"위키 만들어줘"          → generate-wiki (LLM 없음)
"경계 QA 실행해줘"       → qa 에이전트
```

큰 작업 하나가 끝나면 세션을 새로 열고 시작하는 것도 같은 이유로 유리합니다. 하네스는 `CLAUDE.md`와 인덱스에 남아 있으므로 세션을 바꿔도 프로젝트 지식은 유지됩니다.

## 상황에 맞는 스킬을 고른다

`docs/workflows.md`의 의사결정 트리를 외워 두면 대부분의 상황이 정리됩니다.

```text
무엇을 하려고 하나?
├─ 처음 프로젝트 설정             → harness-init
├─ "이거 수정해도 돼?" (정보 수집) → analyze-impact
├─ 실제로 수정 진행                → safe-modify
├─ 새 기능 만들기                  → scaffold-feature
├─ 스택 자체를 바꾸기              → plan-migration
├─ SQL 점검                       → review-sql
├─ "이 코드 뭐하는 거야"          → legacy-decoder (직접 호출)
└─ 변경 후 문서 정리              → doc-syncer (직접 호출)
```

`analyze-impact`는 읽기 전용이고 `safe-modify`는 변경까지 진행합니다. 작은 수정이라면 `safe-modify`만 써도 내부에서 사전 영향 분석을 수행합니다. `scaffolder`(로컬 스킬)는 체크리스트만 보여 주고 `scaffold-feature`(전역 스킬)는 실제 파일을 생성합니다.

### 범용 문구와 확정 슬래시

| 호출 방식 | 예 | 특징 |
|-----------|----|------|
| 범용 자연어 | "수정해줘", "고쳐줘", "버그 잡아줘" | 기본적으로 `safe-modify`를 탑니다. 문맥이 애매하면 다른 스킬로 해석될 수 있습니다 |
| 단축 별칭 | `/modify 주문 취소 버튼 오류 고쳐줘` | 어느 스킬로 갈지 확정됩니다. 뒤의 내용은 본편 스킬에 그대로 전달됩니다 |
| 네임스페이스 슬래시 | `/ax-navi:safe-modify 주문 취소 버튼 오류 고쳐줘` | 다른 플러그인과 스킬 이름이 겹칠 때도 확실합니다 |

운영 반영이나 데모 직전처럼 결과가 중요한 작업에서는 별칭이나 네임스페이스 호출로 스킬을 확정하는 편이 안전합니다. 상황 키워드를 함께 적으면 안전성 판단 기준도 맞춰집니다.

| 상황 | 키워드 예시 |
|------|-------------|
| 운영 서버 반영 | "운영 패치야", "프로덕션 배포 전이야" |
| 긴급 수정 | "긴급 핫픽스야" — 변경 범위를 작게 제한 |
| 레거시 코드 | "레거시 손보는 거야" — 컨벤션 기준 완화 |
| 고객 데모 직전 | "고객 데모 직전이야" — 외부 영향 가중치 높임 |
| 야간 배치 | "야간 배치 관련이야" |

## vibe는 언제 쓰나

`vibe`("알아서 해줘", "그냥 해줘", "바이브로")는 영향도·패턴 적합성·안전성 에이전트 게이트를 생략하는 빠른 모드입니다. 다만 프로젝트 패턴 준수와 가장 작은 테스트·빌드·린트 실행은 유지합니다. 다음 조건에서는 스스로 `safe-modify`(기존 코드)나 `scaffold-feature`(신규 파일)로 승격하므로, 그 경계 안쪽의 사소한 작업에만 쓰는 것이 맞습니다.

- DB 스키마 변경 (DDL, 컬럼 추가·삭제).
- 외부 API 계약 변경 (요청·응답 필드, 엔드포인트).
- 트랜잭션 경계 변경.
- 3개 이상 파일에 걸친 수정.
- 대상 모듈에 검증된 preferred 패턴 프로필이 없음.

작업 도중 승격 조건이 드러나면 그 자리에서 멈추고 승격하며, 이미 적용한 변경도 승격된 스킬의 사전 영향 분석에 포함시킵니다. 범용 요청("고쳐줘", "개발해줘")은 항상 안전 워크플로우가 기본 경로이고, `vibe`는 사용자가 명시적으로 말할 때만 탑니다.

## HOLD/STOP이 나왔을 때 하지 말 것

`safe-modify`는 `어댑터 FULL + 패턴 CONFORM + 필수 검증 exit 0 + change-safety GO`가 모두 충족될 때만 GO를 냅니다. 검증을 실행하지 못했거나 어댑터가 PARTIAL/UNSUPPORTED면 위험 점수가 낮아도 HOLD(`UNVERIFIED`)입니다. HOLD/STOP은 실패가 아니라 사람이 결정할 차례라는 신호입니다.

- 판정을 무시하고 "그냥 적용해줘"로 밀어붙이지 마세요. 자동 수정을 우회하는 경로는 의도적으로 제공되지 않으며, 같은 요청을 `vibe`로 돌려도 승격 조건에 걸리면 다시 안전 워크플로우로 돌아옵니다.
- HOLD 사유를 읽기 전에 재실행하지 마세요. Claude가 이유와 권고 조치를 함께 알려 주므로 그 항목(빌드·수동 시나리오·패턴 근거)을 먼저 확보하는 것이 빠릅니다.
- WinForms Designer·DevExpress·XFDL·JSP/Struts XML 같은 PARTIAL 대상은 실제 빌드·UI·통합 검증 전까지 자동 변경 판정이 HOLD입니다. 이 경우 수동 검증 절차를 준비한 뒤 다시 요청하세요.
- STOP은 현재 방식으로 진행하지 않기를 권고하는 것입니다. 대안을 논의하세요.
- HOLD/STOP으로 끝났고 그 사이 재인덱싱이 있었다면 wiki도 낡은 상태입니다. 종료 보고의 `generate-wiki` 재실행 안내를 따르세요.

## 커밋 정책을 팀에서 정한다

| 경로 | 권장 | 이유 |
|------|------|------|
| `CLAUDE.md`, `.claude/skills/`, `.claude/agents/domain-expert.md`, `.claude/patterns/`, `.claude/ito-guide.md` | 커밋 | LLM 산출물이며 팀원이 pull하면 초기화 없이 바로 사용 |
| `.claude/backup/` | gitignore | 재초기화 전 백업 |
| `_workspace/` (리포트·wiki 등) | gitignore | 재생성 가능한 런타임 산출물 |
| `_workspace/index/*.json` (기계 인덱스) | 팀 결정 | 이식 가능(상대경로·슬래시 정규화·줄바꿈 무관)하므로 커밋하면 팀원은 인덱싱조차 생략. 크기가 부담이면 커밋하지 않아도 팀원이 수십 초짜리 인덱싱 한 번만 더 함 |
| `_workspace/index/_ai_patch.json` | 반드시 보존 | analyzer가 미해결 관계를 판정한 LLM 결과. 다시 만들려면 분석을 다시 돌려야 함 |

`.gitignore`에 `_workspace/`를 통째로 넣으면 `_ai_patch.json`도 함께 버려집니다. 초기화 Phase 3 보고가 이 점을 확인하라고 안내하니, 예외 규칙을 두거나 wiki-hub DB 발행을 대체 경로로 삼으세요. DB에 발행돼 있으면 `publish-wiki --pull`이 인덱스와 `_ai_patch.json`을 복원하며, 순서는 반드시 pull → `--check-stale`입니다.

```gitignore
_workspace/*
!_workspace/index/
_workspace/index/*
!_workspace/index/_ai_patch.json
```

디렉터리 자체를 제외하면 그 안의 파일을 다시 포함할 수 없으므로 위처럼 `*`로 내용만 제외하고 예외를 단계적으로 열어야 합니다.

팀원이 공유 하네스를 pull한 뒤 "하네스 초기화해줘"를 입력하면 LLM 파이프라인 없이 `--check-stale` 판정과 인덱싱만 수행하므로 초기화는 팀당 1회로 끝납니다.

## 파트너 저장소는 자동 커밋하지 않는다

`pair-init`·`cross-repo-scaffold`·`cross-repo-modify`로 백엔드와 클라이언트 저장소를 함께 다룰 때, 파트너 저장소에 대한 커밋은 자동으로 실행되지 않습니다. 반드시 변경 내용을 확인한 뒤 직접 커밋하세요. 각 저장소의 커밋은 하나의 논리적 변경 단위로 나누는 것이 좋습니다.
