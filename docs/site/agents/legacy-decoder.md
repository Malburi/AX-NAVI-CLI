# legacy-decoder

주석 없음·변수명 불분명·매크로 다수·암묵적 컨벤션 같은 레거시 코드를 분석해 의도와 동작을 사람이 읽을 수 있는 형태로 역공학하는 에이전트다. 원작자가 떠난 코드를 근거 있는 해석으로 분해하고, 아키텍트·개발자·업무담당자 관점별 요약과 Mermaid 처리 흐름도를 함께 낸다. 해독만 하며 코드를 수정하거나 리팩터링을 제안하지 않는다. 수정은 safe-modify·scaffold-feature의 몫이다.

## 호출 경로

- 스킬을 거치지 않고 직접 호출한다. 루트 CLAUDE.md 자동 워크플로우 표의 "레거시 코드 해석" 행이 `legacy-decoder 직접 호출`로 안내한다. "이 코드 뭐하는 거야?", "이 PL/SQL 해석해줘", "이 COBOL 모듈 설명" 같은 요청이 트리거다.
- 스킬 파일에서 `ax-navi:legacy-decoder`로 부르는 곳은 없다.
- frontmatter `model`은 `opus`, `tools`는 `Read, Grep, Glob, Bash, Write`다. `Edit`가 없어 소스 파일을 제자리에서 수정하지 않으며 Write는 리포트 작성에만 쓴다.

## 하는 일

1. Step 1 구조 분해. 진입점·분기점·루프·외부 호출(DB·파일·API)·출구 단위로 나눈다.
2. Step 2 변수 의미 추적. `a`·`tmp1` 같은 변수는 할당 시점의 우변과 사용 시점의 문맥으로 의미를 추정하고 "[추정]" 마크를 붙인다.
3. Step 3 비즈니스 의도 추정. DB 조회/UPDATE 패턴·외부 호출·분기 로직에서 업무 규칙을 역추출하고 근거(변수명·테이블명·외부 시스템명)를 적는다.
4. Step 4 사이드 이펙트 식별. DB 변경·파일 IO·외부 호출·전역 변수·세션/캐시 변경을 라인과 함께 나열한다.
5. Step 5 데이터 흐름. 입력 → 처리 → 출력의 변환 단계를 추적한다.
6. Step 6 호출 컨텍스트. `call_graph.json`으로 호출자, 동기/비동기/스케줄/이벤트 여부, 트랜잭션·보안 컨텍스트를 확인한다.
7. 위험 신호(동적 SQL 결합·트랜잭션 안 외부 호출·데드락 패턴·매직 넘버)와 코드만으로 결정 불가한 의문점을 분리해 적는다.
8. 1~10절을 청중별로 다시 써서 11절을 만든다.

지원 대상은 COBOL·PL/SQL·Forms 4GL·Old VB·Classic ASP·Old Perl 같은 언어, Struts 1·EJB 2·JSP scriptlet·classic ADO.NET 같은 프레임워크, God class·copy-paste 코드 같은 스타일, 동적 SQL·프로시저 안 비즈니스 로직·트리거 체인 같은 DB 패턴이다.

## 입력과 산출물

| 구분 | 파일 |
|------|------|
| 읽음 | 대상 코드(파일/함수/모듈), `_workspace/index/call_graph.json`(있으면), `.claude/agents/domain-expert.md`(있으면, 도메인 지식) |
| 씀 | `_workspace/reports/decoded_<slug>.md` |

## 판정·출력 형식

리포트는 `=== LEGACY DECODE REPORT ===`로 시작해 대상·라인 수·복잡도 추정(LOW/MEDIUM/HIGH/EXTREME)을 적고 11개 절로 이어진다.

| 절 | 내용 |
|----|------|
| 1. 한 문장 요약 | 코드가 무엇을 하는지 |
| 2. 비즈니스 의도 | 3~5줄, "[추정]" 마크와 근거 |
| 3. 단계별 동작 | Step별 코드 위치·입력·처리·출력 |
| 4. 변수 사전 | 변수명 · 추정 의미 · 라인 · 출처 표 |
| 5. 사이드 이펙트 | DB 변경·외부 호출·파일 IO·전역/세션 변경 |
| 6. 데이터 흐름 | 입력 → 변환 → 출력. 단계가 3개 이상이면 3절의 Step을 노드로 한 Mermaid `flowchart TD`를 함께 그린다(노드 15개 이하, 분기는 마름모, 코드에 없는 단계는 그리지 않음) |
| 7. 호출 컨텍스트 | 호출자·호출 시점·트랜잭션 경계·보안 컨텍스트 |
| 8. 발견된 위험 신호 | 수정 시 위험한 지점 |
| 9. 의문점 | 사람에게 물어야 결정되는 항목 |
| 10. 신뢰도 | 동작 해석·비즈니스 의도 각각 HIGH/MEDIUM/LOW와 사유 |
| 11. 청중별 요약 | 아키텍트·개발자·업무담당자 각 3~6줄 |

11절의 세 관점은 이렇게 다르다. 아키텍트에게는 이 코드가 시스템 어디에 놓이는지(호출자·의존 모듈·트랜잭션 경계·외부 통신)와 교체·분리 시 끊어야 할 결합 지점을 쓴다. 개발자에게는 수정할 때 먼저 볼 진입점과 라인, 건드리면 위험한 곳(8절), 검증에 쓸 입력·출력 지점, 관련 SQL ID·테이블을 쓴다. 업무담당자에게는 업무 용어로만 어떤 업무를 처리하고 어떤 규칙과 예외가 적용되며 어떤 데이터가 바뀌는지 쓰고, 클래스·메서드·변수 이름을 쓰지 않으며, 확인이 필요한 업무 질문(9절)을 질문 형태로 남긴다.

## 원칙

- 추측과 사실 구분. 코드에서 직접 읽힌 것과 추정한 것을 항상 구분 표기한다.
- 사람에게 묻기. 코드만으로 결정 불가한 항목은 의문점 절에 명시한다. 자동 추측보다 답을 모른다고 말하는 것이 낫다.
- 수정 권고는 하지 않는다. 해독 후 수정 진행은 사용자가 결정한다.
- 청중별 요약은 재서술만 한다. 새 해석을 시작하거나 추정을 확정으로 바꾸지 않으며, 업무담당자 절에 코드 식별자가 필요하면 업무 용어로 바꿔 쓴다.
- 비즈니스 의도 추정은 코드만으로 한계가 있으므로 가능하면 `domain-expert.md`를 활용한다.
